# 04 · QQ 桥接

## 两种仿真模式

| 模式 | 怎么发言 | 沉默 | 适合 |
|---|---|---|---|
| reserved（一代） | 纯文本自动转发，空格分条 | `[SILENT]` | 简单、稳定 |
| reserved2（二代） | 一切皆工具，`qq_send_message` 数组分条 | `qq_mark_read` / 设唤醒 | 有工具、要自主 |

模板推荐 **reserved2**：能控制「什么时候看、回不回、什么时候潜水」。

## 会话映射

```
state/sessions.json
{
  "sessions": {
    "group:<群号>": "session-<id>",
    "private:<主人QQ>": "session-<id>"
  }
}
```

- 一个群一个会话，标题改成群名（好看且好排查）
- 改映射要重启桥（映射是启动时读的）
- 白名单（allow/deny）可以做成热读：按 config.json 的 mtime 重新读

### 私聊路由契约（硬约定）

群聊和私聊走两条不同的路由规则，不能混：

| 来源 | 规则 |
|---|---|
| 群聊 | 可以**创建受限会话**（分身）：禁止文件/终端/桌面/管理工具，只留限定的 QQ 收发工具 |
| 主人私聊 | **只绑定既有主会话**，不允许自动新建替代会话 |

主人私聊绑定的具体行为：

1. 配置里指定**明确的既有主会话 id**，不存在则不投递、只报告，绝不静默新建。
2. 绑定失效（会话被清理 / 重开导致 id 变化）时，**停止投递并在日志与通知里报出来**，等待人工改配置，不自动替换。
3. 桥不修改主会话的模型、预设或工具权限；这些归主会话自己的配置管。
4. 主会话在桌面产生的回复，是否转发到 QQ，是**独立开关**，默认只转发「明确要发出去」的标记内容。

> 如果选择「统一用 reserved2 桥、关掉 Yuuyuko 的宿主侧私聊桥」，可以成立，
> 但必须在 `UPSTREAMS.md` 里补上承担 reserved2 功能的那套桥的仓库与提交，
> 并附一次「私聊消息能被主会话收到并回复」的验证记录。

## 唤醒

一条群消息进来，按顺序判断：

```
@ 我 / 引用我 / 叫名字 / 命中关键词 / 是提问 / 指定发言人 / 概率
```

任何一条命中就排一次唤醒（有合并窗口，默认 8 秒，避免一句话叫醒三次）。

**潜水**：没有唤醒条件命中就不说话。决定收尾前要先等一段观察窗口，
确认没人接着说了再睡，避免「刚说完就走」。

## 分条

二代的「一条」= 数组里一个元素。

- 一条 = 一个意群，能一条说完就一条
- 别一句话一条地挤牙膏
- 单条内不要用空格断句（会被当成分条信号）
- 拆之前自检：拆出来的每句要能独立读通

## 群角色卡

群分身用单独的角色卡（`roles/<名字>.md`）：

- 只写群里的说话节奏与分寸
- 人设以共享人格段为准
- 注入时按模式筛小节（`〔一代〕`/`〔二代〕` 标记）

## 常见故障对照

| 现象 | 先查 |
|---|---|
| 消息不回 | 白名单空 → 日志「忽略未授权会话」 |
| 一条消息两个回复 | 是不是有两套桥同时绑同一会话 |
| 突然全断 | DSH 换端口了；桥要重新发现端口 |
| 配置改了没反应 | 这条配置是不是启动时读的 |
