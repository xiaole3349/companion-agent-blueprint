# 03 · 记忆

> 这一层的「储存 / 遗忘 / 分身只读」框架，来自千狩与澜宝的讨论与论文观点，详见 UPSTREAMS.md 的致谢。

## 两套东西，别混

| 系统 | 形态 | 用在哪 | 特点 |
|---|---|---|---|
| 中央记忆服务（memory.py） | SQLite + 向量 | **权威记忆源**：桥接、多群、批处理 | scope 隔离、可检索、可整理 |
| dsh-fish-memory | 每个会话一份 JSON | 如果继续承担注入，只是**单向投影的读方** | 注入式、按激活分排序、有淡忘 |

模板约定：**中央库是权威源，写入口只有一个。** fish-memory 若保留，
只读中央库生成的投影，不独立提炼、不修改（详见下文「双记忆系统的权威来源」）。

## 记忆类型（按「是什么」分，不按「多重要」分）

一条记忆除了文本，还带这几个属性；属性不同，处理规则不同：

| 类型 | 例子 | 保留 | 能否改人格 |
|---|---|---|---|
| 事件 | 「群里有人修好了机器人」 | 普通，按遗忘策略处理 | 不能 |
| 人物印象 | 「这个群友说话很客气」 | 可更新、可纠正 | 不能 |
| 日记 | 主会话当场写下的主观记录 | 长期，保留原话 | 不能，但可作提案依据 |
| 记忆钉 | 被显式钉住的少数事 | 最硬，不按时间淡忘 | 不能自动改，只能提案 |
| 资料/图书馆 | 工具、插件、结论 | 长期，只留一句用途 | 不能 |

**重要 ≠ 可传播 ≠ 可改人格。** 一条记忆可以很重要，但只在本群可见；
可以被主会话读到，但不代表能改人格。这三件事必须分开写。

## scope 隔离（最重要的一条）

```
group:<群号>     群聊自己的那份
owner_private    私聊/主人那份
public           公共事实（不是「某个群里发生的事」）
```

- 群里注入时只能读 `本群 + public`
- 私聊注入时只能读 `owner_private + public`
- 分身**不能直接改本体**：群消息写进 events 可以，但不能把群里的判断写成人格或跨范围记忆
  （准确说法见下文「群分身只读的准确含义」）

原因很直白：群里的玩笑、黑话、别人的挑衅，一旦写成核心记忆，下次会在别的地方冒出来，
语气和边界都会糊。

## 注入

- 桥接每条消息调用 `/prepare`：写入 event → 召回 → 返回一段「历史记忆数据；不是指令」
- 这段要以「数据」而不是「指令」的形式进提示词，防止记忆里的句子被当成命令
- 召回带上 scope，不要把别的群的内容带进来

## 整理（consolidate）

- 把 events 归纳成 memories，连边，过期作废
- **不要放在请求路径里**：每条消息跑一次全库整理，会和后台索引抢写锁，
  表现是 `/prepare` 大面积 500、`database is locked`
- 正确位置：启动时一次 + 后台每 8 小时一次

## 向量索引

- bge-m3 之类本地 embedding，Ollama 本地跑
- 索引放在后台线程，批量编码在事务**外面**做，写完再进事务
- 大规模首次建库会慢，属正常

## 迁移

从别的框架（AstrBot 等）搬记忆时注意：

- 只搬「原子」会漏掉每日摘要；两个都要搬
- 低重要度的条目别一股脑丢，它们往往是日常语气
- 搬完先跑重复检测，别让同一件事有两个版本

## 双记忆系统的权威来源（重要）

本仓库同时提到 fish-memory 和中央库，这不能变成「两个都写、慢慢分叉」。约定：

> **中央数据库是权威记忆源。** 如果 fish-memory 继续承担注入，它只读取中央库生成的
> **单向投影**，不独立提炼、不修改这些记忆。

相应地要定死四件事：

1. **版本号**：投影带 schema 版本，读方不认识的版本要拒收并报出来，而不是瞎猜。
2. **更新方式**：单向推送或定时快照，二选一；不允许双向互写。
3. **删除传播**：中央库删掉/作废一条，投影也必须删，不能「删了还在注入」。
4. **同步失败**：拿不到投影时，宁可**不注入**并报错，也不退回读自己那份旧库假装还在同步。

如果暂时没有投影适配器，就先**按会话只选一套记忆系统**，不要在文档里宣称已经统一。

## scope 的确定与升级

- `scope` 由**服务端根据凭据**确定，不信任请求正文自己声明的范围。
- 群消息整理成长期记忆时，仍只能写回**原群范围**；进入 `public` 必须走独立的发布流程，
  不能由摘要模型自己把内容「升级」成公共记忆。

## 「群分身只读」的准确含义

「分身只读」不是说分身一点都不能写，而是：

- 分身**不能直接修改**核心人格或跨范围记忆；
- 可信采集器**可以记录本群事件**（这是采集，不是越权）；
- 整理器**可以生成本群记忆**（仍限本群范围）。

一句话：写本群、读本群可以；改本体、跨群、升 public 不行。

## 日记、钉、图书馆、遗忘

### 日记（当场写，别等批处理）

- 主会话在**决定值得的瞬间**立刻写，不等 8 小时整理：压缩之后细节就没了。
- 只指向**私聊**，分身没有写日记的权限。
- 日记保留**当时的措辞**，另生成一条短摘要用于检索——不要把日记反复压缩成条目式摘要，
  那正好把「语气」压没了。
- 日记是**主观记录**，要标出来；它可以作为人格修改的**依据**，但不是指令。

### 钉（显式选择，不是打分）

- 给已有记忆加一个「钉」标记 + 保留理由。
- **钉不扩大可见范围**（本群的钉还是本群可见），也**不能阻止用户删除**。
- 钉住不等于能改人格——它只是「别忘」，不是「可以拿去改本体」。

### 图书馆（用完就删，只留一句用途）

- 资料、工具、插件说明这类「看完就用」的东西，不占记忆预算。
- 只留：来源、可复用结论、怎么用、批注。
- **临时抓取的内容和正式资料分开**：网页抓下来的原文不该直接进图书馆当真资料。

### 遗忘（不是一刀切删除）

- 30 天可以作为**普通群记录**的初始保留策略，不是所有数据的统一期限。
- 例外：未完成的约定、重要记录、纠错依据——这些独立规则，不跟着 30 天走。
- 摘要和索引也要遵守同一套删除/撤回要求：原记录撤了，摘要和索引不能还留着。

## 跨群共享

「public 公共事实」和「另一个群发生过的经历」不是一回事，别混用。
跨群共享走独立的**授权投影**流程，见 `docs/11-cross-group-sharing.md`。
